# 同频 · 相同收藏匹配机制（隐私版）

## 双层匹配
1. **本机私人收藏 × 他人主动公开精选**：本地 JS 用标准 BV 视频 ID 做精确交集，不请求服务器计算，也不发送本机 BV、普通哈希、私人标题、笔记、分类或交集数量。只在本人界面显示“你也收藏了”。
2. **双方主动公开精选**：沿用服务端 `matchPublic`，属于双方自愿公开的共同兴趣，不等于 B站官方收藏验证。

## 数据流
- 服务端 `GET /api/social/candidates?after=<公开用户UUID>`：每页最多 40 个已公开且主动允许被发现的账户资料与精选视频；游标只包含服务端公开用户 UUID。
- 浏览器 IndexedDB 的本地收藏 BV 列表，与返回的公开 `showcase[].bvid` 求交集并排序。匹配函数 `matchLocalFavorites` 从不产生私人笔记字段。界面中使用对方的公开标题，**不显示你的私人标题或私人标签**。
- 未登录可以浏览公开用户并在本机识别重合；点击申请认识时先跳账号页，登录完成后仍需再点击“确认申请”。不能自动发送。
- 对方必须开启“允许发现我”并发布精选才可被找到，退出发现/撤下精选立即失去后续匹配资格。好友申请只有对方接受后才允许聊天。
- **双方纯私人收藏：不支持互相识别。** 没有授权就不尝试扫描、上传或可枚举 BV 哈希；想成为可被发现的一方，可以主动选择公开少量非敏感视频。

## 隐私与功能界限
- 公开资料仍可被有访问权限的人保存，退出发现不能撤回别人此前记住的信息；不声称零知识协议或可验证的匿名集合求交。
- B站播放继续使用原站外链；本项目未获第三方视频播放、图片抓取、官方收藏验证等授权。
- 应用不验证用户是否真正收藏了某个 BV：匹配是用户自行整理的视频兴趣，不是平台认证关系。
- 当前默认自动检索前 120 位公开用户，可通过“继续寻找”逐页检索更多；一页 40 位。生产规模扩大时，若要提升性能，应先设计真正经审查的加密授权式匹配协议，而不是把私人清单发送给服务端。
- 本地列表和隐私仍只保存在本机浏览器 IndexedDB；同账号多端需要自己导出/导入 JSON。
